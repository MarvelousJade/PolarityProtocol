# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity `6000.4.11f1` third-person combat demo built as a portfolio piece: the player places magnetic anchors that pull/push enemies, physics crates, and projectiles. All gameplay code, art, audio, and tooling are first-party — **no marketplace assets or gameplay packages may be added**. Presentation is procedural (Unity primitives + generated materials + synthesized tones).

Read `README.md`, `docs/ARCHITECTURE.md`, and `docs/PERFORMANCE.md` for the shipped feature set, system boundaries, and measured performance claims.

## Architecture

### The scene is empty on purpose

`Assets/PolarityProtocol/Scenes/*.unity` each contain a single GameObject with `ArenaBootstrap` (plus `PerformanceProbe` in the stress scene). **Hand-editing the scenes is pointless** — `ProjectBuilder.GenerateScene()` recreates them from `NewSceneSetup.EmptyScene` on every `BuildDemoProject`. Arena geometry, player, camera, lighting, HUD, and the `Runtime Systems` object are all constructed in `ArenaBootstrap.Start()` (`[DefaultExecutionOrder(-1000)]`), which is also the composition root that wires systems via explicit `Configure(...)` calls.

To change what exists in the demo, edit `ArenaBootstrap` / `EnemyFactory` — not the scene.

### ScriptableObject data is code-generated

`Resources/Data/*.asset` are regenerated by `ProjectBuilder` (`GenerateAbility`/`GenerateEnemies`/`GenerateEncounters`). Hand-tuned inspector values survive only until the next `Build Demo Project`. Persist tuning changes in the code that writes them:

- ability defaults → `AbilityDefinition.ConfigureDemoDefaults()`
- enemy stats → `ProjectBuilder.CreateEnemy(...)` call sites
- encounter waves → `ProjectBuilder.CreateEncounter(...)` call sites (the Encounter Authoring window edits the assets directly, so a rebuild overwrites its output too)

Data is loaded by string path at runtime (`Resources.Load<AbilityDefinition>("Data/MagneticAnchorAbility")`, `Resources.LoadAll<...>("Data/Enemies")`, `"Data/Encounters"` ordered by asset name), so new definitions must live under `Assets/PolarityProtocol/Resources/Data/`. `ArenaBootstrap.LoadAbility/LoadEnemies/LoadEncounters` each carry a full hardcoded fallback so Play Mode works with missing assets, duplicating every tuning value. Change one in `ProjectBuilder`, change it in the matching fallback, or they drift silently.

### Assemblies

`PolarityProtocol.Runtime` (no references, engine only) ← `PolarityProtocol.Editor` (Editor platform), `PolarityProtocol.EditModeTests`, `PolarityProtocol.PlayModeTests`. Tests reference Runtime only, so nothing in `Editor/` is testable and Runtime code must never reach into `UnityEditor`.

Tests never load a scene: they build what they need with `new GameObject()` + `AddComponent` + `Configure(...)`, then `Object.Destroy` it. Follow that pattern — anything requiring `ArenaBootstrap` to have run is not testable as written.

### Dependency direction and the static seams

No service locator — dependencies flow data → simulation → orchestration → presentation, wired by `ArenaBootstrap`. The deliberate exceptions are a handful of statics set in `Awake` and cleared in `OnDestroy`; use these instead of `FindObjectOfType`:

- `GameSession.Active` — run state, score, pause/restart
- `ProjectilePool.Active` — the only way to create projectiles; neither player nor AI instantiates them
- `FeedbackBus.Pulse(freq, duration, volume)` / `FeedbackBus.HitStop(duration)` — audio and hit-stop
- `DebugOverlay.Enabled` — F3 diagnostics gate
- `EnemyBrain.ActiveCount` — cheap enemy count for the benchmark

### Magnetics

`MagneticForceSolver.Calculate` is a pure static function (no colliders, no components) — that is where force-behaviour tests belong. `MagneticAnchor.FixedUpdate` does the spatial query with a fixed 64-collider `Physics.OverlapSphereNonAlloc` buffer plus a `HashSet<MagneticTarget>` to dedupe compound colliders. `MagneticTarget` adapts the force to a `Rigidbody` (`ForceMode.Acceleration`) and forwards side effects: `EnemyBrain.NotifyMagneticForce` for displacement, `Projectile.RedirectByPlayer` for ownership transfer. AI state is never edited by magnetics directly.

A target configured `resistsDisplacement` (the shield robot) still reports the field to its listeners but takes no force — that separation is what lets its plate tear off while the unit itself stays planted. Report-without-move is the seam to reuse for any future magnet-immune object; do not drop the `MagneticTarget`, or the owner stops hearing anchors at all.

### Combat

`DamageInfo` is the shared message; `DamageReceiver` → `Health`, with any `IDamageModifier` on the same GameObject transforming it in between (`Health.CacheModifiers` scans `GetComponents<MonoBehaviour>()`). `EnemyBrain` implements the interface itself and reduces frontal damage only for the Shield archetype while unexposed — so projectile code stays ignorant of enemy types. Add per-enemy damage rules through this seam, not through `Projectile`.

### UI

Player-facing UI uses one runtime Unity UI Toolkit document created by `HudController`. Structure lives in `Resources/UI/PolarityInterface.uxml`, shared status-bar structure in `StatusBar.uxml`, and presentation in `PolarityStyles.uss`; C# owns state, cached value updates, focus, and button events. Keep this as a focused UI layer rather than introducing a UI framework or third-party dependency. The F3 `DebugOverlay.OnGUI` path intentionally remains IMGUI for developer diagnostics only.

### Input

Legacy `UnityEngine.Input` only — the new Input System package is **not** installed. All bindings live in `LegacyInput`; add new ones there. Right-stick look needs the `Right Stick Horizontal`/`Vertical` axes that `ProjectBuilder.AddInputAxis` injects into `ProjectSettings/InputManager.asset` (`SafeAxis` swallows the exception if they are missing).

## Constraints to respect

**Runtime-created materials need their shaders in the Always Included list.** `RuntimeArt.Material` calls `Shader.Find("Standard" | "Sprites/Default" | "Legacy Shaders/Diffuse")`; nothing references those shaders from an asset, so a player build strips them and everything renders magenta. `ProjectBuilder.EnsureAlwaysIncludedShaders` adds them — extend that list when introducing any new runtime `Shader.Find`.

**Allocation discipline is a documented performance claim** (Gen-0 collections 17 → 4, see `docs/PERFORMANCE.md`). Avoid per-frame allocations on gameplay paths: no LINQ or scene searches in `Update`/`FixedUpdate`, cache materials and component references, reuse pooled objects, and keep expensive enumeration behind `DebugOverlay.Enabled`. Feedback tones are a prewarmed bank of 15 clips snapped to the nearest frequency — don't synthesize per pulse.

Physics and AI movement run in `FixedUpdate`; presentation and input in `Update`.

Re-run the benchmark and update `docs/PERFORMANCE.md` if a change plausibly affects frame time or GC.
